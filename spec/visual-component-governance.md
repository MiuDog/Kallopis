# 視覺元件統一維護與 Catalog 驗收

階段：DEFINE／Iteration（既有元件的尺寸、風格與使用契約收斂）。

狀態：NOT READY。使用者已要求統一維護、資料式 API、統一文件範式與先行 Catalog；下列 open 決策尚未接受，不得當成實作授權。

語意責任：Kallopis 視覺元件契約，涵蓋元件可宣告內容、組裝規則與人類視覺驗收。不新增程式模組；既有 styling、features、composition、rendering 的實作責任留待 PLAN 配對。

目標版本：本輪視覺契約 v1（提案，非套件版本）。完整能力目標為所有公開視覺元件均有維護責任、使用文件與 Catalog 證據；舊入口的收斂時程待 VG-03 決定。

## 責任與範圍

- 本庫視覺維護責任由本任務統籌並以持久文件交接；人類接受視覺品質。這不是對其他工作階段的技術鎖定，也不能保證單靠文字規則阻止違規修改。
- 其他 agent 使用已公開能力；能力不足時提出需求，不自行增加產品專用 Widget、節點、renderer、樣式變體或替代預設值。
- 視覺維護包含可用控制、容器、組合元件及相關狀態；「所有公開」需依 library 實際可達性盤點，不能只掃類別名稱或既有 Catalog。
- 本輪 DEFINE 產物為當前規格及待決策項；不修正 renderer、不改尺寸、不建立正式元件，不提前切 BUILD 任務。
- 上游 BlockNote 正文模型、排版、選取與 undo 仍由 KLP-0020 指定的權威負責；Kallopis 維護語意風格與宿主，不建立第二份正文實作。
- 不新增 theme、environment、l10n 或資料寫入權威。

## 嚴格組裝契約（VG-02 已接受方向）

使用者確認：允許受限組裝，但尺寸、樣式及組裝規則均由本庫嚴格規定。以下為此方向的驗收要求；各元件的具體資格表仍須在後續契約中明列。

| 管制項目 | 必須具備的契約 |
| --- | --- |
| 元件身分 | 可渲染能力與插槽種類由本庫封閉擁有；外部不得藉自訂 type ID 或任意 node／slot 介面實作取得新能力。Explorer 已接受的 item interface 允許 consumer 實作及 method 包裝，依其資料／能力契約驗證，不要求 KLP 具體 class；此擴充不取得新 renderer 或元件 ID。 |
| 父子關係 | 每個具名插槽明列可接受的元件及用途；不能以「實作了通用 KlpNode」作為充分條件。 |
| 結構規則 | 必填／可選、最少／最多數量、順序、互斥／相依、允許的巢狀位置與重複使用規則都有明確定義；可自由排序或遞迴也必須明列。 |
| 上下文規則 | 同一元件能否用於工具列、側欄、正文、浮層等位置，由契約決定；不能因局部型別相符而忽略祖先或區域限制。 |
| 排版選擇 | consumer 只能使用本庫公開且適用於當前位置的語意選項；不能用任意 flex、空白節點、無間距或巢狀容器繞過尺寸與組裝規則。具體保留哪些既有選項仍須逐項審核。 |
| 資料與事件 | consumer 提供業務資料、資料來源及已定義的語意事件；不能透過 callback 回傳原生呈現或建立另一條視覺樹。合法策略或組裝函式的結果仍受相同規則驗證。 |
| 更新與平台 | 初次組裝、資料驅動的結構更新及自適應策略套用相同契約。無效新樹不得部分生效，亦不得先觸發該樹的安裝或業務事件。 |
| 拒絕行為 | 未定義的組合預設不允許。診斷指出節點路徑、插槽、違反規則及允許值；不靜默移除、重排、換元件或補樣式使其勉強顯示。 |

「最嚴格」表示允許範圍明確且不可繞過，不代表每個畫面只能使用一個固定模板。consumer 可在本庫明列的範圍內選擇與組裝，不能自行擴張該範圍。

驗收須同時涵蓋合法組合及違規反例；文件禁令不能取代可執行的契約約束。編譯期與執行期如何分工屬於 PLAN，不在 DEFINE 決定實作機制。

## API 文件共用範式（交付需求，非新 API 設計）

每個元件使用同一章節順序：

1. **用途與可用狀態**：解決什麼需求、公開入口、支援環境、正式／實驗／相容狀態。
2. **如何宣告**：必要及可選資料、預設行為、資料權威、事件輸入／輸出；最小可執行範例。
3. **如何組裝**：完整列出父容器／插槽、允許子項、角色、數量、順序、互斥／相依、巢狀與上下文限制，提供合法組合及會被拒絕的反例；未列出的組合不得由 agent 推測可用。
4. **如何更新**：資料更新後的可見反應、事件處理、選取／展開等狀態歸屬。
5. **布局與視覺保證**：尺寸由誰決定、長文字／空內容／空間不足時的行為；引用統一風格契約。
6. **不合法或不支援的用法**：錯誤如何呈現、替代的公開組裝方式或能力申請入口。
7. **Catalog 與接受狀態**：對應 specimen、狀態覆蓋、已接受版本與未解事項。

全庫另需一張組裝資格索引，讓讀者能回答「這個元件可放在哪裡」與「這個容器能放什麼」。不存在或無 renderer 的能力標示未提供，不以假範例冒充。

實際層級、檔案定位、功能名稱與契約卡提案見 [功能維護入口](../docs/ai/feature-contracts.md)。固定名稱需求已接受；具體名稱為文件提案，不藉此新增架構模組或宣稱各功能契約已完成。

## Catalog 檢查契約草案

以下為 VG-04／VG-07 的討論提案，尚未接受具體外觀或工具實現：

- 以圖片涉及的控制家族作第一組：文字＋圖示操作、純圖示操作、側欄列、分區標頭、視窗控制；其餘家族列清冊。
- 同頁並列基準與少量候選，一次聚焦一項決策；保留相同內容、視窗與縮放，以便比較。
- 同時提供一般外觀與幾何檢查，分辨布局範圍、可見表面、點擊命中區；陰影不等於可點擊面積，除錯布局框不等於實際命中區。
- 建議控制底面對應主要命中區；小圖示或觸控需要擴大命中時使用明確用途規則，不能重疊到相鄰操作。實際容許差異待人類比較後接受。
- 依元件能力展示正常、hover、focus、pressed、selected、disabled 等適用狀態，以及長文字、空資料、窄空間和文字縮放；不替不存在的狀態發明行為。
- 概念候選明確標示為視覺提案；正式驗收需使用實際庫內元件，包含真實布局與輸入。不能拿另一份手工外觀或靜態圖片證明命中正確。
- 候選狀態至少區分待檢查、需修改、已接受；接受紀錄指出適用元件、狀態、平台與尺度，不把一張桌面截圖擴大解讀為所有平台皆已驗收。

## 現有證據與衝突

- 使用者提供兩張 Planist 圖片，一張含布局除錯標記、一張為正常外觀。這是問題回報；尚未執行 hit-test，也無法由圖片確定錯誤根因或宣稱無人維護。
- [KLP-0019](decisions/KLP-0019-declarative-framework-migration.md) 已規定封閉元件與受限組裝，同時保留舊視覺 API 至對應遷移完成。VG-03 未決前維持既有相容承諾。
- [風格 v1](style-v1.md) 與 [8px／微立體](frame-relief-8px.md) 是現有風格依據；後者取代 Frame 間距的 12px 條款，不改 12px Frame 圓角。
- [畫面組裝指南](../docs/ai/screen-composition.md) 仍寫 12px Frame 間距與無陰影，與較新已接受契約不同；列為文件收斂事項，不作新風格依據。
- [現有 Catalog](../docs/ai/catalog.md) 只展示部分宣告式能力，不能視為全公開元件已覆蓋；文件描述仍有待遷移控制及 renderer。
- 現行 API 已包含受限組裝、callback、資料來源、完整 primitive set 與封閉 surface／spacing 選項；不能僅因型別是 Dart 資料便認定符合使用者本次期望。
- 直接讀取的 API 中，`KlpNode`／`KlpScreenBody`／`KlpLayoutNode` 為公開 abstract interface，`KlpFrameGroup.content` 接受 `List<KlpNode>`，布局節點也暴露整數 flex。這些均需對照嚴格契約盤點；本次未檢查完整驗證鏈，不據此宣稱它們已能繞過執行期限制。
- 已檢查 Git 狀態，工作樹有大量既存未提交修改；本任務保留它們。DEFINE 不執行產品測試，不宣稱畫面已修復。

## 消費端案例的所有權

Planist Sidebar 的結構、功能選用與組合邏輯移至 [Planist 組裝規格](../../Planist/docs/planning/sidebar-composition.md)，由使用者在 Planist 設計；本庫只引用為通用元件的使用與驗收案例，不維護第二份產品組裝真相。

Kallopis 提供通用元件組、資料／事件契約、視覺及合法組裝規則。Planist 在合法範圍內自由組合；採用哪些功能、排列順序、導航目的與商業行為均屬 Planist。Agent 無權用「合法」替代使用者的產品設計。

本庫可驗證一般插槽、角色、數量及結構限制，不得將 Planist 特有的專案／待辦／資產名稱、固定順序或操作流程編入本庫 catalog／renderer／validator。功能缺口須先抽象為產品無關能力，再進入本庫 DEFINE。

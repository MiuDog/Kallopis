# 通用視覺規範維護規則

日期：2026-10-11。適用範圍：Kallopis 共通視覺規範與各框架對應文件。

## 單一權威

[設計規範索引](KALLOPIS-DESIGN-MAP.md) 及其六份章節是正式視覺規範。採用來源是既有統整表；本次分檔不改設計。各章節各自擁有一類內容，禁止在 README、框架庫或網頁手寫第二份相同表格。

| 內容 | 唯一維護位置 | 修訂原則 |
| --- | --- | --- |
| 記號、單位、運算、繼承、預設解讀 | `notation.md` | 解析含義改變必須列出受影響的配方 |
| 原料名稱與數值 | `primitives.md` | 相同值不等於相同用途；既有名稱不可任意合併 |
| 全域用途與 theme 對應 | `semantics.md` | 保留語意 ID；不能因單一框架 API 改名而改通用用途 |
| 元件角色、尺寸、variant 與狀態配方 | `recipes.md` | 保留繼承關係與既有狀態規則；未定義的組合先明示缺項 |
| 使用例子 | `examples.md` | 引用既有 primitive／semantic／recipe，不自行新增預設 |
| 已知差異與平台限制 | `platform-notes.md` | 明示差異、來源及適用框架；不把現存差異靜默正規化 |

## 修訂程序

1. 依責任定位唯一章節；先查既有 ID、來源與平台差異。
2. 格式、錯字與導覽修正可直接處理；改數值、用途、繼承或合法組合屬設計契約變更，須有已接受的需求。
3. 修改該章節，更新直接受影響的引用、例子與框架對應；同一規則不在多處複製維護。
4. 檢查 ID 唯一、引用存在、繼承無循環，以及原先的 `none`、繼承與產品決定等不同含義仍完整。分檔或搬移須逐項比對，不能用數量相同代替內容相同。
5. 以版本控制差異記錄修訂；重大契約變更由決策文件記錄原因，正式規範只保留當前有效規則。

本次分檔已驗證六個原始章節串接與原檔逐字一致；只在導覽及來源描述上另外修訂。後續修訂不能沿用這次驗證宣稱仍與舊快照一致。

## 框架對應

Flutter、React 等框架庫從正式規範取得語意與數值，框架文件只維護通用 ID → 公開 API 的對應、單位／色碼轉換、資產接入及能力限制。元件組合應引用相同語意與配方；產品保有畫面和業務流程的決定權。

既有規範含 Flutter 來源名稱與現存 resolver 差異，這些是追溯及對應資訊。其他框架落實時應明確對應其結果；不能把 private `lib/src`、Flutter 型別或 `context.klp` 當成跨框架使用入口。

若平台能力無法落實某條契約，先列明該條 ID、能力差異與可觀察結果，再處理框架契約；不能假稱已符合，也不能為了實作方便反向改設計。

## 匯出與交換

目前 JSON、CSS 及 ZIP 為 2026-10-05 的匯出快照；不是另一份可獨立修改的設計權威。本次沒有重建這些產物，也不宣稱它們已具備正式規範的自動同步能力。

產物若需要更新，必須從同一次已接受的規範及框架對應重建或核對；未完成同步時明示版本與缺項。可攜單檔可在後續由正式章節組合產生，不回到人工維護完整副本。

## Docs 網頁整合契約

正式規範應整合到既有 `tool/reference_site` 文件站；網頁從上述 Markdown 來源產生，不維護另一份文章。網站已依此契約直接產生正式章節；操作方式見 [網站工具](../../tool/reference_site/README.md)。

| 要求 | 可觀察驗收 |
| --- | --- |
| 文件入口提供通用視覺規範 | 從 docs 首頁可進入本索引；與 Flutter API Reference 的用途可區分 |
| 分章閱讀與互相引用 | 六份章節與維護規則均有頁面；相對 Markdown 連結轉為網站路由，適用 GitHub Pages 專案前綴 |
| 保留表格與記號 | token／配方表格呈現為真正表格；程式記號、色碼與公式不遺失；窄畫面可讀完整欄位 |
| 搜尋可定位內容 | 可以 token 名稱或配方 ID 找到對應章節，而不只搜尋文章標題 |
| 單一來源及完整性 | 網站來源清單與索引一致；缺來源、缺頁或無效內部連結不可冒充完整整合 |

網站提供正式表格、章節連結與全文搜尋，並驗證來源、頁面、搜尋內容及內部連結。React 的生成器也直接讀取本規範；`react/src/source-manifest.json` 記錄來源雜湊與 ID 清單。生成資料是框架產物，不取代正式 Markdown。
